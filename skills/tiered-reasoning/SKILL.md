# Tiered Reasoning

Route a user-owned problem tier into an actual execution setting and, at T3,
protect causal diversity until evidence-governed synthesis.

## Boundary

- Require Tier: T0, Tier: T1, Tier: T2, or Tier: T3 for the current problem;
  otherwise ask.
- Propagate that tier verbatim to descendants of the same admitted problem;
  never change it or reuse it elsewhere.
- Map T0 to low, T1 to medium, T2 to high, and T3 to xhigh.
- Apply effort before substantive execution. If the root cannot change its
  running setting, keep it as conductor and request a fresh executor with an
  explicit effort override. Proceed only when the runtime confirms application;
  otherwise record unknown and return blocked unless the user revises the contract.
- Record requested tier, effective effort, application boundary, and baseline.
- Tier never changes authority, assurance, scope, budgets, or acceptance.

## Routing

| Tier | Workflow |
|---|---|
| T0 | One direct executor; no candidate portfolio; focused oracle. |
| T1 | One primary mechanism; add a fresh challenge only when material. |
| T2 | Explore the structural choice; use a fresh alternative when two mechanisms remain credible; use a fresh verifier. |
| T3 | Run at least three causally distinct operators, then fresh adjudication and conditional final verification. |

## Freeze the common packet

Before branching, freeze the outcome, primary invariant, owner, authority,
budgets and implementation cap, raw evidence and provenance, baseline identity,
workloads, metric aggregation, tie-breaks and materiality threshold, measurement
protocol, oracle identity and hash, failure boundaries, and recovery. Prefer a
clean commit. Otherwise seal a baseline tuple of commit, staged and unstaged
patch hashes, allowed untracked path hashes, and scoped tree digest. Materialize
and verify that digest in every lane or stop.

Every lane uses atomic mapping and the brutalist order:

question -> delete -> simplify -> expose the owner -> state the causal mechanism
-> falsify -> accelerate -> automate

Share the discipline, not the resulting map. Each lane maps its own atoms so an
operator can challenge another lane's assumed owner, boundary, or representation.
Do not delete safety, observability, recovery, or discriminating evidence.

## T3 operator portfolio

The minimum portfolio contains:

1. factorization: preserve causal direction while separating axes, ownership,
   interactions, and repeated work;
2. inversion: change control, ownership, proposal, verification, flow, or commit
   topology; and
3. representation change: reframe the primitives or transfer a structurally
   analogous mechanism.

Before execution, each lane must name a different owning mechanism or state
transition and a distinguishing falsifier. Reject cosmetic variants. T3 needs at
least three candidates; a hybrid or repair consumes the frozen implementation
cap or requires a revised contract.

## Candidate separation

Give each operator a fresh context and, for writable repository candidates, a
separate worktree from the same baseline. In a cooperative blind pass, do not
expose sibling reasoning or outputs. Namespace mutable resources; credentials
and external side effects require separate authority controls. Prevent writes to
the frozen benchmark or oracle and confirm their identities around each run.
Claim enforced isolation only with a permission or sandbox receipt; worktrees
share Git metadata and are not a security boundary.

Each lane returns one normalized receipt:

```text
operator and atomic map
causal thesis and owning mechanism
artifact or patch identity
predicted and observed metric effects
critical assumptions and cheapest falsifier
cost and complexity
failure and recovery boundary
outcome classification
```

Freeze evaluation budgets and metric weights before results appear. For noisy
metrics, freeze environment, warmup, repetitions, run order, aggregation, and
tie-breaks under the governing policy. Serialize measurements through one oracle
runner when concurrent work would contaminate them.

## Adjudication and verification

Start adjudication from the untouched baseline in a fresh context and, for
repository candidates, a fresh worktree. Initially provide the common packet,
candidate artifacts, normalized receipts, and common oracle results, not
generator transcripts. Reject contract, authority, invariant, oracle, and budget
violations first.

Adjudication may select a dominant candidate, construct a compatible and
falsifiable synthesis, or reject all candidates. Never average incompatible
assumptions or merge every diff. Treat a hybrid as a new candidate and rebuild
only its necessary mechanism from the baseline.

If adjudication seals an artifact, give it to a fresh verifier without candidate
identities or rationale. Rebuild independently and run the sealed correctness,
boundary, recovery, scaling, and performance oracles. Confirm oracle identities
around the run; unchanged is not independent evidence by itself. Do not repair
inside the verifier. Without a sealed artifact, return the evidenced outcome.

Return verified win, verified no-gain, invalid, blocked, or inconclusive.
