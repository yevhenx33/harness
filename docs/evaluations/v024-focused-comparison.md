## Inputs and method

Baseline: v023 package at `33ace59b8f1fa8a370728d1ce21d63b64d116a3f`.
Candidate: v024 after the user's correction to continue routine setup repairs
without renewed approval. Root policy and current snapshot remain byte-identical;
source identities are frozen in the [results](v024-decision-results.json).

Both arms used CLI 0.166.0, configured `gpt-6.1-sol`, low effort, the same six
situations and independent oracles from the [existing plan](v024-comparison-plan.md),
and the same seven source paths: root policy, architecture, implementation-slice,
latency-optimization, github, and vector data-model/storage references. Selected
sources were supplied directly; this did not test skill discovery or routing.
The immutable backend model revision was not exposed.

Two fresh ephemeral sessions ran sequentially, each capped at 180 seconds, with
read-only sandboxing, isolated temporary homes, configuration/rules ignored,
matching tools, and expected oracles withheld. Scenario execution and tool use
were explicitly prohibited. Neither session made a tool call or timed out.
Review against the frozen oracles was unblinded; full replies and limitations
are retained rather than replaced by scores alone.

this evaluator incorrectly overrode the reserved `openai` provider. Their exit
codes, stderr, identities, and zero scored cases remain under
`invalid_setup_attempts` in the results. They are not policy failures or erased
attempts. Initial process times were 0.080 and 0.100 seconds; usage was unavailable.

A configuration-only check then parsed the corrected invocation. Twelve requested
feature disables were honored, but `unified_exec` remained true despite its flag.
That check did not qualify tool isolation. The completed sessions used matching
read-only controls and no observed tool calls; feature output is not substituted
for actual transcript evidence.

The user first granted a one-time exception for two evaluation sessions, then
explicitly instructed correction of the harness and continuation without repeated
approval. The revised root rule distinguishes setup failures from executed trials,
requires in-scope setup correction within existing budgets, and preserves explicit
all-invocation caps, no-retry boundaries, and valid unfavorable experimental results.
It creates no general exception for delegation, production writes, or release.
